# AWS Day 1 — Cloud Computing and AWS Foundations

## Objective

Build the mental model required to evaluate AWS infrastructure as a Backend and Product Engineer, using the Betting Operations Management Platform as the architecture laboratory.

## Track Context

AWS Foundations is a parallel learning track with independent numbering. It does not replace, advance, or renumber the main engineering journey.

The track prioritizes practical architectural and operational competence over certification preparation. Sessions follow an architecture-first method: questions, trade-offs, decisions, and then implementation or review when justified.

## Architecture Scenario

The Betting Platform requires a Rails API and PostgreSQL today, with Redis, Sidekiq, file storage, centralized logs, monitoring, and secure credential management expected later.

The session considered a first production deployment with:

- users primarily in Brazil;
- a small initial budget;
- limited current server-administration experience;
- a preference for reducing operational burden;
- an architecture that can evolve without premature complexity.

## Questions Explored

- Why choose AWS when the company already owns an on-premises server?
- How does responsibility change when using EC2?
- What is gained and lost by choosing Amazon RDS instead of managing PostgreSQL on EC2?
- What fails when Rails and PostgreSQL share one EC2 instance?
- What constitutes a single point of failure?
- Does separating Rails and PostgreSQL create high availability?

## Core Mental Models

Cloud computing provides computing resources on demand through programmable interfaces and usage-based pricing. It provides capabilities, but it does not automatically produce a secure, scalable, observable, or highly available architecture.

The shared-responsibility distinction is:

> AWS is responsible for security **of** the cloud.  
> The customer is responsible for security **in** the cloud.

For an EC2 workload, the customer remains responsible for:

- updating the guest operating system;
- configuring network and security rules;
- securing Rails and its dependencies;
- preventing application vulnerabilities such as SQL injection;
- protecting credentials and configuring AWS security services correctly.

AWS remains responsible for the physical facilities and underlying hardware, including replacement of failed physical equipment.

## Trade-offs Identified

### Reasons to Use AWS

- delegate physical data-center security;
- avoid purchasing, maintaining, and replacing physical equipment;
- reduce part of the infrastructure-maintenance burden;
- direct more engineering capacity toward product development.

### Cost

AWS cost is an important disadvantage and operational risk, but AWS is not inherently always more expensive than on-premises infrastructure. A meaningful comparison includes hardware, electricity, cooling, connectivity, physical security, backup infrastructure, unused capacity, and employee time.

Usage-based infrastructure also introduces a distinct risk: resources can be provisioned easily and continue generating charges unless cost is actively monitored and controlled.

### Amazon RDS for PostgreSQL

The initial preference is Amazon RDS because current server-administration experience is limited and database operations are not the product's differentiator.

RDS reduces responsibility for:

- physical infrastructure;
- operating-system maintenance beneath the managed database;
- PostgreSQL installation;
- automated backup infrastructure;
- hardware replacement;
- parts of patching and monitoring.

The product team still owns:

- schema and migrations;
- query performance and indexes;
- permissions and database access;
- network configuration;
- backup-retention choices;
- restoration and recovery testing;
- capacity selection;
- cost monitoring.

The accepted trade-offs for learning purposes are:

- higher visible service costs;
- increased AWS dependency;
- less low-level administrative control;
- possible restrictions on PostgreSQL extensions and configuration.

This preference is not yet an application-level deployment decision.

## Failure Analysis

Running Rails and PostgreSQL on one EC2 instance creates one failure domain:

- an instance failure makes both the API and database unavailable;
- the EC2 instance is a single point of failure;
- the design is not highly available.

Separating Rails onto EC2 and PostgreSQL onto RDS is a proportionate first improvement. It separates the application and database failure domains and reduces database operational work.

It still does not create complete high availability because the single Rails EC2 instance remains a single point of failure. Multiple application instances behind a load balancer and an RDS Multi-AZ configuration may be considered later when availability requirements justify their cost and complexity.

## Technical English

Expression of the day:

> What trade-offs are we accepting?

Consolidated explanation:

> For the Betting Platform, I would initially run the Rails API on EC2 and PostgreSQL on RDS. This approach reduces the database administration burden and separates the application from the database failure domain. It does not provide complete high availability because the Rails instance remains a single point of failure, but it is an appropriate starting point for the product's current stage.

## Key Learning

Managed services transfer selected operational responsibilities; they do not transfer engineering accountability. The service model determines which responsibilities remain with the team.

A simple architecture can be appropriate when its remaining failure modes, costs, and limitations are understood explicitly.
