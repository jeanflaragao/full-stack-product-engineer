# AWS Day 2 — VPC, Subnets, Security Groups, and Failure Boundaries

## Objective

Build the first concrete network architecture for the Betting Operations Management Platform on AWS and develop the ability to diagnose connectivity failures without introducing unnecessary operational changes.

## Track Context

AWS Foundations is a parallel learning track with independent numbering. It does not replace, advance, or renumber the main engineering journey.

This session continued the architecture-first method from AWS Day 1: reason about responsibilities and security boundaries first, then introduce the AWS mechanisms that implement them.

## Architecture Scenario

The working deployment model remains deliberately simple:

```text
Internet
   |
   v
EC2 / Rails API
   |
   v
RDS / PostgreSQL
```

The goal is not yet high availability or production implementation. The goal is to understand how these resources should be placed and connected securely inside AWS.

## Concepts Explored

- VPC as the application's private network boundary inside AWS;
- public and private subnet responsibilities;
- Security Groups as traffic-control boundaries;
- why PostgreSQL should not be exposed directly to the public internet;
- Security Group references between the application and database tiers;
- the distinction between component health and end-to-end system health;
- evidence-driven incident diagnosis;
- total cost of ownership when comparing self-managed PostgreSQL with RDS.

## VPC Mental Model

A VPC is the private network boundary in which the application's AWS resources are placed.

The initial conceptual architecture is:

```text
VPC
|
|-- Public Subnet
|   `-- EC2 / Rails API
|
`-- Private Subnet
    `-- RDS / PostgreSQL
```

The application tier needs a path for user traffic. The database tier does not need direct internet exposure.

The key reasoning is:

> Exposure should follow responsibility.

Rails exists to receive application requests and communicate with required external services. PostgreSQL exists to serve the application and should therefore remain behind a narrower network boundary.

## Public and Private Subnets

The working mental model established in this session is:

- the Rails EC2 instance belongs to a public application tier because the API must receive internet traffic;
- the RDS PostgreSQL database belongs to a private data tier because only the application should need database connectivity;
- subnet placement and routing determine whether a network path can exist;
- Security Groups determine which traffic is allowed across that path.

This distinction will be refined in the next session when route tables, Internet Gateways, public IPs, and NAT behavior are introduced.

## Security Group Model

A simplified ruleset for the first architecture is:

```text
EC2 Security Group
Inbound:
- HTTPS TCP 443 from approved internet sources

RDS Security Group
Inbound:
- PostgreSQL TCP 5432 from the Rails application Security Group
```

The database should not use a rule such as:

```text
TCP 5432 from 0.0.0.0/0
```

because `0.0.0.0/0` represents all IPv4 addresses and would unnecessarily broaden the attack surface.

A key learning was that a Security Group can be referenced as the source of another Security Group rule. This allows the architecture to express:

> The application tier may access PostgreSQL.

rather than binding database access to one particular EC2 private IP address.

This matters when application instances are replaced or eventually scaled.

## Administrative Database Access

The session intentionally did not select a final AWS mechanism for administrator access to production PostgreSQL.

The requirement was established first:

> Administrative access should enter through an authenticated and controlled path into the AWS environment rather than requiring the production database to be publicly exposed.

The concrete mechanism remains future learning work.

## Failure Analysis

The session analyzed four independent failure scenarios.

### Scenario A — EC2 instance failure

- RDS may remain healthy;
- Rails becomes unavailable because its host is unavailable;
- restarting only the Rails process is insufficient when the underlying EC2 instance has failed;
- the EC2 instance must be restored, restarted, or replaced.

### Scenario B — RDS unavailable

- EC2 may remain healthy;
- the Rails process may still be running;
- requests requiring PostgreSQL fail;
- restarting Rails does not repair the database outage.

### Scenario C — Rails process failure

- EC2 can remain healthy;
- RDS can remain healthy;
- Rails becomes unavailable;
- restarting the Rails process may be an appropriate recovery action when evidence confirms the process itself is the failed component.

### Scenario D — EC2-to-RDS network path blocked

- EC2 may be healthy;
- Rails may be running;
- RDS may report healthy or available;
- the application can still be effectively unavailable because Rails cannot reach PostgreSQL.

This established an important operational principle:

> Healthy components do not necessarily mean a healthy system.

## Incident Diagnosis Exercise

The session examined an incident with the following evidence:

```text
EC2 status:     healthy
Rails process:  running
RDS status:     available

Rails log:
PG::ConnectionBad
connection to PostgreSQL on port 5432 timed out
```

The correct first response was not to restart RDS without evidence.

The investigation should instead test the hypothesis that the network path between the application and database is broken.

The diagnostic model introduced was:

```text
symptom
   |
   v
observation
   |
   v
hypothesis
   |
   v
evidence
   |
   v
action
```

A concrete configuration error was then identified:

```text
RDS Security Group
TCP 5432 from sg-old-rails

Current EC2 Security Group
sg-betting-api
```

The appropriate correction was to update the RDS Security Group rule to trust the current application Security Group rather than replacing or restarting otherwise healthy resources.

The operational principle reinforced was:

> Do not introduce a second outage while investigating the first one.

## External Service Connectivity

The session also clarified that Rails requiring outbound access to a third-party service does not imply that RDS should receive internet access.

The desired responsibility boundaries remain:

```text
Internet -> Rails          allowed as required
Rails -> Internet          allowed as required
Rails -> RDS :5432         allowed
Internet -> RDS            not allowed
```

The concrete mechanisms for outbound routing will be studied later.

## RDS and Total Cost of Ownership

AWS Day 1 introduced the EC2-versus-RDS trade-off. Day 2 refined the cost reasoning.

Running PostgreSQL on the same EC2 instance may have a lower visible infrastructure price, but it also makes the engineering team responsible for more database operations, including installation, backup infrastructure, patching, upgrades, recovery, monitoring, and operational failure handling.

RDS has a higher visible service cost but can reduce operational burden and engineering time.

The comparison should therefore consider total cost of ownership rather than only the monthly AWS bill.

RDS still does not remove application and database engineering responsibilities. The team remains responsible for areas such as:

- schema design and migrations;
- queries and indexes;
- application/database compatibility;
- access configuration;
- backup and retention choices;
- recovery testing;
- capacity and cost decisions.

## Consolidated Architecture

The final Day 2 mental model is:

```text
VPC
|
|-- Public Subnet
|   `-- EC2 / Rails
|       `-- Security Group
|           `-- allow HTTPS traffic as required
|
`-- Private Subnet
    `-- RDS / PostgreSQL
        `-- Security Group
            `-- allow TCP 5432 from the Rails Security Group
```

The user can explain the reasoning behind this architecture:

- EC2 runs the application and needs application-level internet connectivity;
- RDS hosts PostgreSQL and should be reachable only by the application tier;
- the database should not be publicly exposed merely for convenience;
- Security Groups restrict allowed traffic between responsibilities;
- network failures can make a system unavailable even when individual components report healthy.

## Technical English

Natural architecture explanation developed during the session:

> I will create a VPC for the application network. Inside the VPC, the EC2 instance will run the Rails application in a public subnet because it needs to receive traffic from the internet. The RDS PostgreSQL database will be placed in a private subnet because it should only be accessed by the application. Security Groups will restrict traffic so that the Rails application can receive HTTPS traffic, while RDS only accepts PostgreSQL connections on port 5432 from the EC2 application Security Group.

Useful expression:

> I would evaluate the total cost of ownership rather than comparing only the monthly infrastructure cost.

## Key Learnings

- A VPC is the network boundary for the application's AWS resources.
- Public/private placement should follow resource responsibility and routing needs.
- Security Groups restrict which traffic is permitted.
- PostgreSQL should not be exposed to `0.0.0.0/0` merely to simplify administrative access.
- RDS can trust an application Security Group instead of a single EC2 IP address.
- Component health and system health are different concepts.
- Operational changes should follow evidence rather than guesswork.
- Managed services should be evaluated using total operational cost, risk, and engineering time, not only service price.
