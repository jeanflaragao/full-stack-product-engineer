# Day 37 — Bookmaker Destruction Boundary

## Objective

Design and verify the bookmaker-destruction boundary against the application's current executable domain.

## Context

The application had no `Account` model, `accounts` table, bookmaker-account association, or active-account lifecycle. Nevertheless, premature Account-related code implied an active-account deletion rule that the domain could not execute.

## Architectural Questions

- What behavior belongs in `Bookmakers::DestroyService` today?
- Which concerns belong to the service boundary and which belong to HTTP?
- Should a future active-account invariant exist in production code before the Account domain exists?
- Does the current implementation provide enough evidence to accept ADR-0002?

## Boundary Distinctions

`Bookmakers::DestroyService` owns the application operation and synchronously destroys the supplied bookmaker. The HTTP boundary owns authentication, resource visibility, status codes, and structured error responses.

Service specs verify application behavior independently of HTTP. Request specs verify the external API contract, integration flow, and database effects.

## Decisions

Following YAGNI, remove `Bookmakers::ActiveAccountsExistError`. Reintroduce an equivalent exception only when the Account domain exists and supplies a real business invariant.

Remove the premature `Accounts::CreateService` placeholder because its path created an invalid Zeitwerk autoloading contract. Future requirements belong in the roadmap or documentation rather than dormant production code.

Keep ADR-0002 Proposed. The intended exception-propagation boundary is clearer, but no real business workflow currently demonstrates a known application exception propagating from a service to the HTTP boundary.

## Implementation and Tests

- Added a service spec proving that `Bookmakers::DestroyService` deletes the supplied bookmaker.
- Strengthened the successful request spec to verify `204 No Content`, an empty body, and deletion of the intended record.
- Verified that another user's bookmaker and a nonexistent bookmaker return the structured `resource_not_found` contract without changing database state.
- Verified that an unauthenticated request returns `401 Unauthorized` without changing database state.
- Removed premature Account-related code.

## Key Learning

A plausible future rule is not current domain behavior. Executable invariants require real domain concepts and lifecycle semantics; introducing their exceptions and service placeholders early makes the codebase less truthful and can break framework contracts.

## Next Logical Step

Design the Account domain when product requirements are ready. Revisit bookmaker deletion only after that domain defines a real active-account invariant, and accept ADR-0002 only after a genuine workflow validates its service-to-boundary propagation contract.
